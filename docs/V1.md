# Max Ultra MCP v1

Max Ultra MCP v1 separates the agent-facing MCP process from the singleton 3ds Max bridge.

```text
ChatGPT Desktop / Codex / Claude Code / other MCP client
        │ MCP JSON-RPC on STDIO
        ▼
core/server.js --stdio       one process per agent client
        │ authenticated CONTROL protocol on 127.0.0.1
        ▼
core/server.js --daemon      one process per machine/port
        │ persistent TCP connections
        ▼
01_START_MAX_ULTRA_MCP_FIRST.ms in each open 3ds Max
        │ main-thread command queue
        ├── scene / viewport / MaxScript / renderer
        └── process-scoped Windows UI Automation
```

The daemon never publishes a network endpoint beyond loopback. `CONTROL call` and shutdown operations require a per-user 256-bit token stored by default below `%LOCALAPPDATA%\3DGROUND\MaxUltraMCP\runtime\state`. This stable location survives MaxPkg package-root replacement, while `MAX_ULTRA_MCP_TOKEN_FILE` can override it. Probe and inventory remain compatible with the MaxScript bootstrap.

## End-user installation

> **ChatGPT Desktop users: switch to Codex mode before using Max Ultra MCP.** Run the connection test and all 3ds Max requests in Codex mode. Ordinary ChatGPT mode does not expose this local MCP connection. A green **MCP ready** status confirms registration, not the mode or tool access of the current conversation. This mode requirement does not apply to Claude Code or other compatible MCP clients.

**Claude users:** open the Claude desktop app, sign in, and use **Code > Local** on this Windows computer. AI Client Setup uses the Claude Code CLI to register MCP for that local session. Terminal chat is not required. Ordinary Chat, Cowork, Cloud, and WSL sessions are outside this setup. Reopen the local Code session and run **Test prompt**.

Release archives include official portable Node.js 24 LTS under `runtime\win-x64`; users do not install Node, edit PATH, use administrator rights, or download packages at runtime.

Run this one file inside every 3ds Max process that should be available:

```text
01_START_MAX_ULTRA_MCP_FIRST.ms
```

The file starts the daemon/Max bridge, then waits two seconds before starting one hidden AI registration-readiness check. The operation has a 75-second timeout and is not repeated periodically. It checks the shared ChatGPT Desktop/Codex registration, user-scoped Claude Code registration, and global Antigravity settings; these results do not claim that an AI chat is currently connected. When all supported client results are conclusive, no supported registration exists, and the user has not dismissed setup, it opens **AI Client Setup**. A failed check remains visible for manual retry and does not open setup automatically. **1. Setup** provides official CLI registration plus exact portable-runtime STDIO values for manual and other-client configuration. **2. Test prompt** copies a safe read-only verification prompt. Each client has a direct setup button with its own status. Missing Codex and Claude Code CLIs offer a confirmed official installer, with cancellable indeterminate progress. After CLI verification, a missing desktop opens its official page in the default browser for manual installation. Antigravity skips the CLI step. Refresh status verifies desktop presence; Connect remains separate. Available Antigravity also uses a Connect to label. See [CLI installation](README.md#cli-installation) for budgets and account steps. Already configured registrations are not reinstalled on repeated clicks. The manual STDIO section can be collapsed; Refresh status and Test prompt remain available. Antigravity setup uses a backed-up, verified update of its server entry in global settings, preserving other settings. Its configured status only verifies matching settings; use the Test prompt for connection evidence. Codex and Claude registration continue to use their official CLIs.

Closing setup saves only the dismissed flag and leaves the bridge running. That flag suppresses automatic opening, not the delayed status check or immediate manual refresh. The aggregate client status and **Settings -> Open AI client setup...** both reopen setup. Restart or reconnect an AI client after adding the server. The legacy `scripts\install-chatgpt-codex.bat` is optional for headless OpenAI registration.

`version.ini` is the canonical product version. `scripts\prepare-release.ps1` synchronizes release metadata, `core\package.json`, and `CHANGELOG.md` before verification. The installed MaxScript UI reads the package version from `manifest.ini` and falls back to `version.ini` in a source checkout. Maintainers prepare the release runtime with `scripts\prepare-portable-node.ps1`. It downloads a pinned official Windows x64 Node archive, verifies it against the official `SHASUMS256.txt`, preserves the Node license, and verifies the resulting executable version. `scripts\build-release.ps1` then creates a clean versioned ZIP and adjacent SHA-256 file. The next single-executable step is prepared in [SEA.md](SEA.md) but remains experimental until signed-PE and ownership tests pass.

## Main panel contract

The in-Max controller and all owned windows use Python and Qt Widgets. The root MaxScript is a thin loader for `python/bootstrap.py`. Node.js remains the MCP server and router. Python background workers handle I/O; Max calls and Qt mutations stay on the main thread.

The main panel starts at 640 x 480 and can shrink to 240 x 180. It retains AI setup, refresh, hide, scene context, the journal, lifecycle actions, Skills, Settings and Donate. At narrow widths actions become icon-only. Above 1024 logical pixels controls grow; at 1800 they grow again. See [UI_DESIGN.md](UI_DESIGN.md) for exact breakpoints, focus, shadows, rounded controls and the Skills loading overlay.

The journal is SQLite-backed outside the installation, paged in the view, searchable, filterable and exportable. It has no 30-entry UI cap. Selection and reading position are preserved, while auto-scroll follows only at the end. Wide rows wrap; narrow rows elide. MCP responses retain their independent bounds.

Seven editable JSON themes apply immediately across open windows. The Max theme reads colorMan. SVG actions use Lucide assets. Settings is modal, supports persistent opacity, and dims other owned windows. The mini-panel reflects readiness with green, amber or red and remains inside monitor work areas.

## Manual MCP configuration

```toml
[mcp_servers.max-ultra-mcp]
command = "C:\\Users\\USER\\AppData\\Local\\3DGROUND\\MaxUltraMCP\\runtime\\win-x64\\node.exe"
args = [
  "C:\\Users\\USER\\AppData\\Local\\3DGROUND\\MaxUltraMCP\\core\\server.js",
  "--stdio"
]
startup_timeout_sec = 20
tool_timeout_sec = 600
default_tools_approval_mode = "writes"

[mcp_servers.max-ultra-mcp.env]
MAX_ULTRA_MCP_TOOL_PROFILE = "archviz"
```

Use absolute paths. If a development checkout has no packaged runtime, Node.js 22+ can be used temporarily; release users should always receive the portable runtime.

The integration follows [OpenAI's MCP configuration documentation](https://developers.openai.com/codex/mcp). Local STDIO is the v1 target. ChatGPT Web requires a remote plugin-backed MCP connection or a secure tunnel and must not expose the local daemon port directly.

Claude Code registration follows [Anthropic's MCP documentation](https://docs.anthropic.com/en/docs/claude-code/mcp) and uses `--scope user` so the same local server is available across projects for the current Windows user.

- `archviz`: 83 tools; core plus materials, material diagnostics, guarded Normal/Smooth modifier review, and structured floor-plan validation/build.
- `full`: 88 tools; archviz plus generic modifiers, import/export, and animation helpers.

The thirteen core layer tools use scene-bound LayerRefs and bounded main-thread operations. Destructive operations require a state-bound preview token; native hierarchy Undo limitations are explicit. See [Semantic layers](LAYERS.md) for policies, properties and acceptance fixtures.

`max_skills_list` and `max_skill_read` run in the STDIO host without connecting to the daemon or Max. They also dispatch through the runtime for authenticated bridge clients. They read a shared per-user skill store but never share Max selection state. `max_skill_read` accepts a namespaced ID, optional content revision, relative path, and bounded text offset/limit; image assets are returned as MCP image content. The Skills window uses a separate local helper for explicit import/delete actions, not MCP mutation tools. ZIP import accepts one exact SKILL.md at root or in one enclosing folder. core/skill-zip.js validates central/local records, safe paths, case-insensitive collisions, file types, decompression bounds and CRC before passing owned temporary staging through the same package validator. Store/Deflate with UTF-8 (or ASCII) names are supported; encrypted, split and ZIP64 archives are rejected. Staging is deleted on completion/failure/cancellation; the one-step Import actions validate the package and preserve internal content-revision checks before saving. See [Custom skills](CUSTOM_SKILLS.md).

## Read-only diagnostics CLI

`core/cli.js` is a client-neutral diagnostics companion to the existing daemon and STDIO host. It never starts another server and exposes only `status`, `setup`, `skills`, `health`, `capabilities`, `help`, and `version`. `health` and `capabilities` use the authenticated loopback control client with fixed read-only MCP tool names; there is no arbitrary tool or MaxScript command.

`status` checks both Codex and Claude Code through their official read-only `mcp get` and `mcp list` operations, then probes the existing daemon and connected Max inventory. `setup` only prints reviewed `codex mcp add` and `claude mcp add ... --scope user` commands. It never edits either client configuration.

Skill discovery scans package-local `skills/*/SKILL.md` frontmatter and the Markdown files below each skill folder. It reports each dynamic name, description, absolute/relative path, and referenced `max_*` capabilities. `skills --check` compares those references with live `max_capabilities`; missing references are evidence for the agent, not permission for the CLI to execute a fallback. Workflow interpretation and execution remain with the agent and MCP.

The source-only `diagnostics/Max Ultra MCP Diagnostics.bat` chooses the bundled runtime when available, falls back to development Node.js, and forwards arguments to `core/cli.js`. The launcher is deliberately absent from `maxpkg-files.txt`; `core/cli.js` remains package-local for agent diagnostics without changing the normal `01_START_MAX_ULTRA_MCP_FIRST.ms` user flow.

Tool calls return a stable structured envelope:

```json
{
  "ok": true,
  "data": {},
  "warnings": [],
  "error": null,
  "hints": [],
  "sceneRevision": 4,
  "durationMs": 18
}
```

Known error codes include `BRIDGE_DOWN`, `MAX_NOT_CONNECTED`, `INSTANCE_REQUIRED`, `VALIDATION_FAILED`, `TIMEOUT`, `JOB_CANCELLED`, `JOB_NOT_FOUND`, `JOB_NOT_COMPLETE`, `JOB_LIMIT_REACHED`, `JOB_TYPE_MISMATCH`, `STALE_PLAN`, `MATERIAL_DIAGNOSTICS_INVALID`, `UI_ELEMENT_NOT_FOUND`, `UI_CAPTURE_FAILED`, `RENDERER_UNSUPPORTED`, and `STALE_NODE_REF`. Error envelopes include a short recovery hint when the client can take a predictable next step.

Each STDIO host owns its selected Max id and render jobs. Two different MCP clients can therefore use one daemon without changing one another's routing. One connected Max routes automatically; multiple instances require `max_select_instance`.

Re-running `01_START_MAX_ULTRA_MCP_FIRST.ms` marks the new bootstrap as a replacement start. Off the Max main thread it probes the current daemon, acquires the bounded lifecycle mutex, checks whether another Max shares the daemon, reads the package-local control token, requests `shutdown_owned` with the exact probe identity, waits for the endpoint to close, and only then launches the replacement. A daemon shared by another Max is reused rather than interrupted. A legacy or unverified endpoint is never killed. The AI-client-owned STDIO host survives a replaced daemon and coalesces later tool calls behind one verified reconnect attempt for up to ten seconds on the same configured loopback endpoint. It exits only when its MCP stdin closes or it receives a process termination signal. In-flight calls return one `BRIDGE_DOWN` response and are not replayed automatically.

One STDIO host per active AI-client session is expected. `node_repl.exe` is an AI-client worker and is outside Max Ultra MCP ownership; no lifecycle path enumerates or terminates arbitrary Node.js processes.

Write tools carry MCP destructive/write annotations. Arbitrary `max_execute` and UI automation additionally carry `openWorldHint`. `sceneRevision` is an opaque monotonic integer seeded from a new nonzero revision epoch for each daemon process. Semantic mutations increment it; a supplied `NodeRef.sceneRevision` from an older daemon or scene state is rejected.

## Transport and reload limits

The persistent Max connection uses explicit newline framing over bounded byte reads. A partial frame has a five-second completion deadline and a 4 MiB limit; connect is limited to two seconds and synchronous stream reads/writes to one second. Socket close accompanies cancellation. Each inbound/outbound queue accepts up to 64 frames and 8 MiB of ASCII wire content; pending main-thread requests retain the 100-request cap plus an 8 MiB content cap. Overflow closes the connection or rejects admission explicitly. These are content limits, not exact managed-heap limits.

The daemon admits at most 64 pending requests per Max and 256 across instances, with an 8 MiB per-instance pending-content and socket-write budget. Rejected requests are not sent. `REQUEST` appends an optional sixth field containing an absolute UTC deadline in Unix milliseconds; legacy five-field requests remain accepted. The updated bootstrap checks this deadline immediately before dispatch and processes the currently buffered inbound controls before executing pending work. Cancel is best effort once dispatch begins: arbitrary synchronous MaxScript cannot be safely interrupted, and a timeout must never cause automatic replay.

The main timer rejects nested callbacks and checks its lifetime after operations that can pump messages. Re-running the entry point and automatic update installation use a separate deferred timer when shutdown is pending. This timer waits without blocking the UI, never reloads while the main Tick is active, and allows up to 30 seconds for worker completion after that callback returns. A timeout retains the old facade and reports a retryable failure. Worker handlers and arguments remain retained until `IsBusy` becomes false. A .NET argument reference roots the worker while running, with explicit .NET lifetime control on its MAXScript wrapper. Runtime thread-id checks reject main-thread transport execution and non-owner timer execution; they do not establish native runtime stability.

See [bridge stability acceptance](BRIDGE_STABILITY.md) for the remaining real-Max fixtures. Existing one-shot endpoint probes are separate from the persistent framing path.

### Common jobs and plan tokens

`max_job_list`, `max_job_status`, `max_job_wait`, `max_job_cancel`, and `max_job_result` provide one session-owned lifecycle for long operations. Existing `max_render_status`, `max_render_wait`, `max_render_cancel`, and `max_render_get_result` remain compatibility wrappers over the same registry. A job created by one MCP client is not visible to another client.

The shared plan-token module canonicalizes operation bindings and can bind a future plan to its operation, selected instance, scene revision, targets, capabilities, request, and relevant external state. Verification uses constant-time token comparison. Existing polygon and floor-plan validation tokens use the same canonical hashing implementation while preserving their v1 payload-only contract.

### Material diagnostics

`max_material_find_unassigned` scans without changing selection. It returns bounded NodeRefs grouped as `noMaterial`, `invalidMaterial`, `emptyMultiSubSlot`, `unsupportedMaterial`, and `materialMissingMaps`. Missing-map detection currently proves missing `Bitmaptexture` inputs; renderer-specific file slots remain the responsibility of the planned `max_assets_scan` workflow. The result reports scanned, matched, returned, truncated, per-category counts, and coverage limits rather than overstating completeness.

### Automatic updates

Automatic update discovery and verified MZP staging run in a hidden detached PowerShell helper whose network requests use Windows `curl.exe`. Only the small result INI is polled on the Max main thread. After verification, the bootstrap disposes the active bridge, installs the MZP through MaxPkg, and restarts itself from the updated package.

### Native code policy

The default and release-critical path remains Node.js plus the MaxScript main-thread bridge. No C++ component is required.

A future managed C# helper may be bundled inside the MaxPkg package and loaded from its package-relative path with `dotNet.loadAssembly`. It may provide version-neutral Windows, serialization, hashing, or compute helpers, but it must remain optional, require no GAC/registry/admin installation, and have a tested Node.js/MaxScript fallback.

An ordinary managed DLL is not a safe substitute for a version-matched 3ds Max SDK plug-in. C++/CLI mixed-mode assemblies and native P/Invoke helpers have runtime and ABI constraints, and arbitrary SDK calls from a loaded DLL must not bypass 3ds Max plug-in initialization or the main-thread rule. If profiling eventually justifies direct SDK access, ship an optional per-Max-version GUP/managed plug-in through the package, detect it through capabilities, and preserve full operation without it. Autodesk documents package-file assembly loading through [`dotNet.loadAssembly`](https://help.autodesk.com/cloudhelp/2023/ENU/MAXScript-Help/files/Interaction-with-Other/DotNet-In-MAXScript/GUID-9BE82D70-1869-46D7-9501-E5453E25AC68.html) and separately documents the lifecycle requirements of [GUP plug-ins](https://help.autodesk.com/cloudhelp/2026/ENU/MAXDEV-CPP-API-REF/class_g_u_p.html).

### Polygon mesh creation

`max_validate_polygon_mesh` accepts object-local vertices and zero-based polygon faces without touching 3ds Max. It normalizes physical units and computes bounds, triangle/quad/n-gon counts, quad ratio, polygon Element count, maximum valence, and high-valence vertices. It reports blockers for invalid indices, duplicate or degenerate faces, synchronous size limits, and non-manifold edges unless explicitly allowed. With `subdivisionReady:true`, n-gons, inconsistent winding, and isolated vertices become blockers while controlled triangles and high valence remain explicit warnings. `requireSingleShell:true` is optional because one Editable Poly may legitimately contain multiple polygon Elements.

`max_create_polygon_mesh` requires the unchanged payload and SHA-256 validation token. The Max-side script creates one mesh, adds polygon faces with `meshop.createPolygon`, converts it to Editable Poly, and returns a NodeRef plus measured vertex, edge, face, and open-edge counts. Physical values use `units.decodeValue`; scene unit settings are never changed. Bulk polygon creation disables internal undo snapshots while one named outer undo record retains the object creation.

The synchronous path is intentionally bounded at 10,000 vertices, 20,000 polygons, 256 vertices per polygon, and 100,000 total face-vertex references. Larger geometry requires import or a future cancellable geometry job.

### Viewport capture and orientation

`max_capture_viewport` always executes `max tool maximize` before reading the active viewport bitmap. Because the command is a toggle, the Max-side handler compares the viewport pixel area before and after it and toggles once more when the first call made an already-maximized viewport smaller. The active viewport remains maximized after capture.

The default `clean-realistic` review preset temporarily switches the active Nitrous viewport to Realistic, raises viewport anti-aliasing to 8X, and hides the active grid, edged faces, selected edged faces, selection brackets, selection overlay/outline, and hover preview overlay/outline. `clean-shaded` applies the same cleanup with Shaded mode for material-independent topology and normal-orientation checks. `clean-current` preserves the current visual style while applying the cleanup. Every preset restores all saved display, selection, grid, and anti-aliasing settings after the PNG is written; a restore failure is reported instead of claiming clean success.

Agents should use `max_set_view` for standard views, `max_activate_camera` for camera composition, and `max_frame_selection` or `max_zoom_extents` before capture. Use `clean-realistic` for normal visual review, `clean-shaded` for topology or normal A/B checks, and `clean-current` only when the deliberately selected viewport style is evidence. A free perspective orbit is available through a small reviewed `viewport.rotate` MaxScript fallback documented in the packaged agent skill. Camera views must be composed by transforming the camera, not by pretending a failed viewport orbit succeeded.

`max_frame_selection` runs the documented `max zoomext sel` command against the active viewport. `max_zoom_extents` runs `max tool zoomextents`, which frames all scene objects in the active viewport. The invalid `max zoomext all` spelling is rejected by regression tests; the `all` suffix belongs to `max tool zoomextents all` and is reserved for explicitly changing every viewport.

`max_execute` remains intentionally unrestricted and is the escape hatch for a Max use case that has no semantic tool yet.

## Rendering

`max_render_start` returns immediately with a `jobId`. Production rendering runs through the selected Max main-thread queue and saves a PNG result. `max_render_status`, `max_render_wait`, and `max_render_get_result` do not block MCP initialization or tool discovery.

Cancellation sends Escape through the process-scoped external UI adapter, which remains available while the Max main thread is rendering. Corona and V-Ray interactive starts/stops are capability-guarded; unknown APIs return `RENDERER_UNSUPPORTED`. Generic production render works with the active 3ds Max renderer. Generic render progress is `null` when the renderer exposes no stable progress API.

`max_renderer_properties_get` is read-only and inspects the active renderer through `getPropNames renderers.current` plus a bounded `show renderers.current` report. It returns the renderer class, exact property-name array, raw diagnostic output, total character count, and truncation state. This proves runtime discoverability for the installed renderer build; it does not claim that every property is writable or that similarly named properties share semantics across renderers.

Every execute request also carries a bounded, privacy-safe activity label. `max_run_script`, `max_run_script_file`, and `max_execute` require the caller to name the exact operation in `activity`, so the in-Max panel can show `Create wall openings via MaxScript [12ab34cd]`, `Assign tree materials via MaxScript`, or `Delete opening helpers via MaxScript`. Missing or generic names are rejected instead of being logged as an ambiguous operation. Script contents and local paths are never copied into the activity log. Lifecycle messages use a separate `system` category and color so initialization, health, connection, and update status remain visually distinct from scene operations.

## UI automation boundary

The PowerShell/.NET UI Automation adapter revalidates the target PID and requires the process name `3dsmax.exe`. It never searches or controls another desktop application.

Selectors support HWND, AutomationId, exact/partial name, class, control type, and index. Operations prefer UI Automation patterns over coordinates. `max_ui_send_keys` focuses only a verified Max-owned element. UI inspection may be limited when 3ds Max is elevated but the MCP process is not, or when a third-party plugin exposes no UI Automation accessibility tree.

`max_ui_capture_window` has a native HWND path for MAXScriptDialog, WinForms, plugin, and other Max-owned windows. When `window.hwnd` is supplied, the adapter checks that the handle exists and belongs to the selected `3dsmax.exe` PID, then rechecks ownership immediately before `PrintWindow`. It uses a screen-copy fallback only when `PrintWindow` reports failure. This path does not repeat the UI Automation window search, so an HWND returned earlier by `max_ui_list_windows` or `max_ui_inspect` remains usable while the native window is valid. The response reports `selectorSource` and `captureMethod`.

`max_ui_diagnostics` is the explicit, read-only diagnostic path. It accepts the same `window` selector plus `maxDepth` and `limit`, and returns:

- `window`: verified native bounds, client bounds, visibility, class, DPI, and scale.
- `uia`: the bounded accessibility tree; `maxDepth` applies here.
- `native`: the bounded HWND tree with parent/depth relationships, rectangles, class names, and `isWinForms` / `isWebBrowserServer` markers.
- `webBrowsers`: one stable entry per embedded MSHTML `Internet Explorer_Server`, including client/document/body/layout/scroll dimensions and available zoom/DPI values.
- `limitations`: capability notes that agents should preserve when reporting conclusions.

`limit` is enforced independently for the UI Automation and native trees, up to 1,000 entries each. Normal calls should keep the default 200. DOM values are nullable: MSHTML may omit a property, the document may still be loading, or cross-integrity accessibility may be blocked.

For a MaxPkg or other standalone dialog, use this exact sequence:

1. Call `max_list_instances` and explicitly select the only or uniquely identified Max instance.
2. Call `max_ui_list_windows` with a narrow `titleContains` value.
3. Take the returned decimal `hwnd` and call `max_ui_capture_window` with only `window.hwnd` for visual evidence.
4. Call `max_ui_diagnostics` with the same `window.hwnd`, starting with `maxDepth: 5` and `limit: 200`.
5. Use `uia.controls` for semantic selectors, `native.controls` for real HWND geometry and WinForms hosting, and `webBrowsers` for clipping, scroll, zoom, or DPI diagnosis.
6. Repeat capture after a UI change and verify the image; diagnostics describe structure and measurements, not semantic success.

Native WinForms entries cover HWND-backed controls. Windowless managed controls may appear only through UI Automation. WebBrowser DOM metrics are available only for the legacy WinForms MSHTML engine, not Chromium/WebView2 or custom renderer surfaces. `PrintWindow` can still be unsupported by GPU or layered plugin windows; when the reported method is `screenCopyFallback`, an overlapping desktop window can affect pixels. UI access can also be restricted when 3ds Max runs elevated and the MCP process does not.

A runnable field/button/verification rollout is available in the source repository under `tests/fixtures/ui-automation-rollout`; test fixtures are excluded from production packages.
The automated helper fixture verifies direct HWND capture, evidence fields, bounded native diagnostics, and output cleanup without opening 3ds Max. The mock protocol suites verify tool schemas and envelopes. A real-Max fixture is still required to prove child/MAXScriptDialog and plugin/WebBrowser behavior inside supported 3ds Max versions.



Example sequence for a third-party script:

1. `max_run_script_file`.
2. `max_ui_wait` for its window.
3. `max_ui_inspect` or `max_ui_find`.
4. `max_ui_set_value` / `max_ui_select`.
5. `max_ui_invoke`.
6. `max_capture_viewport` and visual verification.

## Floor plan from an image

See [`examples/house-plan-from-image`](../examples/house-plan-from-image/README.md).

The vision-capable model reads the attached drawing and calls `max_validate_floor_plan` with structured millimeter values. Explicit prompt values take precedence; otherwise readable dimensions, dimension chains, legends, and scale marks in the image are authoritative. Pixel proportions are used only for unlabelled geometry after a reliable labelled scale is established, and workflow defaults apply only when a value is absent from both prompt and drawing. Ambiguous or conflicting critical dimensions require a specific user question before validation. Validation checks ids, dimensions, wall references, vertical fit, overlapping openings, floor outline, counts, and bounding box, then returns a SHA-256 `validationToken`. `max_build_floor_plan` recomputes the token and refuses changed data.

The builder preserves current Max system units by converting millimeters with `units.decodeValue`. It first creates joined wall-footprint splines and keeps that SplineShape as a hidden, unchanged source object. It copies the source, applies Extrude to the copy, collapses only the working copy, and rebuilds outward-facing opening-aware wall topology through `meshOp` before converting the result to Editable Poly. No Boolean cutter is used. Ordinary endpoint corners are mitered, branch-wall endpoints are trimmed to the receiving wall face, and unsupported complex junctions are reported instead of being hidden by deliberate wall penetration. Door/window Dummy helpers are not created. The response includes guarded `sourceSpline` and `wallMesh` NodeRefs for subsequent verified operations.

The default floor outline is interpreted as a wall-centerline perimeter and offset to the outside faces of matching perimeter walls before downward extrusion. `floor.outlineMode: "finished"` preserves an explicitly supplied final slab edge. The complete build remains one undo transaction.
